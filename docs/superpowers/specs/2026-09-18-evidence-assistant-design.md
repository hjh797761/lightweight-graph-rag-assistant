# 轻量证据关联助手：第一版设计

日期：2026-09-18。用户已确认产品方向、口头方案及本书面规格，进入实施计划。
本文是可修改的设计说明，不新增冻结 contract、校验散列或发布 gate。
本次文档提交不表示运行代码、索引迁移或效果验证已经完成。

## 1. 目标与边界

保留 SQLite、本地 embedding、可选 cross-encoder、离线检索和现有回答接口，
将默认问答升级为“找到核心证据，按明确关系补充语境，并说明来源与限制”。
主要面对有章节、条款及文档内引用的中文资料；没有可靠结构的资料仍能检索，
但不得声称恢复了其章节或语义关系。

第一版不增加关系抽取 API，不训练排序模型，不部署独立图数据库，不增加
OCR、复杂表格理解、跨文档实体合并或自动多跳推理。不承诺事实正确性或
证据完备性，也不改造认证、已有安全措施及非本项目的集群任务。

全部新文件在 D 盘本项目目录。模型验证先在本机 CPU 上进行；GPU 验证仍
由用户通过已有集群环境手动提交。不自动 SSH、不重装集群环境、不重跑旧实验。

## 2. 当前实现与改造依据

检查基于代码提交 `66bb5a9`：

- `retrieval.py` 当前把向量、关键词、共现图、主题等异质分数相加，启用
  cross-encoder 后再以它的分数替代。图的收益需要通过候选或证据组织体现，
  不能仅以“保留旧加分”为目标。
- `full` 的关键词循环将零命中的片段也加入候选，正常服务把全部候选送入
  reranker；外部比较脚本却有独立的候选截断。一个八片段、向量候选上限二的
  内存检查中，vector 重排二片段，full 重排八片段。
- 当前概念是正则截取的词串，共现边没有关系类型及证据定位；不应把它解释
  为可靠的事实关系。
- 现有 `clean_text` / `context_text`、序号、事务写入和独立服务接口可复用。
- 之前纯向量小规模 GPU 结果支持继续改善轻量路径，但不证明新设计有效。

## 3. 方案选择

采用分阶段排序与证据补全。暂不采用需要校准数据的分数加权或学习排序。

流程：向量与词项召回 → RRF 融合 → 有上限的重排 → 核心证据选择 →
有限结构关联 → 预算内上下文组装。

三个职责分开：

1. 召回：是否把可能有用的片段找进来。
2. 排序：哪些片段直接回答问题。
3. 关联：哪些原文片段提供被引用的条件或局部语境。

第三步的选择理由不能伪装成第二步的相关性概率。

## 4. 多路召回和排序

### 4.1 词项检索

使用 SQLite FTS5，建库与查询采用相同的领域无关词项规范化：Unicode NFKC、
拉丁字符小写、保留英文及数字标识符，在连续中文段内产生字二元组；只有一个
汉字的连续段保留该单字。不跨标点拼接二元组。不把这些词项叫作实体，也不扩充专门针对
现有评测题目的词典。

预分词文本只用于索引，原文和来源位置不改写。查询词项由程序构造为受控的
字面量查询，不直接执行用户提供的 FTS 查询表达式。使用 BM25 顺序产生词项
候选，空词项列表贡献空结果。FTS5 不可用时报告明确的依赖问题，不静默改成
全库扫描；用户仍可显式选择纯向量模式。

### 4.2 RRF

各通道按片段 ID 去重，排名从一开始。采用等权：

`fusion_score(d) = sum(1 / (rrf_k + rank_m(d)))`

只对实际出现的通道求和，初始 `rrf_k=60`。同分以片段 ID 稳定排序。
这是常用的起始设置，不是本项目已验证最优的参数。

先限定各路返回规模，再限定融合候选及重排数量。第一版建议向量及词项各
取至多 40，融合重排至多 40；上限在核心实现中执行，服务与评测均复用。
不能通过把零命中项放进字典来扩大候选。

### 4.3 重排及解释

启用重排时核心候选以 cross-encoder 分数降序排列；同分依次按融合排名和
片段 ID 排列。主动关闭重排时使用 RRF。加载失败仍明确报错，不能悄悄关闭。

解释记录每条候选的召回通道、各路排名与原始分数、融合分数、重排分数和
最终去留原因。某通道未运行或该片段未被打分时记录为空，而非伪造零分。
任何分数都不叫正确率或经过校准的置信度。

旧配置的原始加分逻辑保留为显式可选模式，但重排数量也接受核心上限约束；
这是有意的行为修正，需在更新说明中披露。历史结果文件不修改，也不声称
新旧 legacy 运行在这一点上完全相同。

## 5. 文档结构与关联

### 5.1 来源信息

新建库为片段保存文档 ID、稳定序号、章节 ID／标题路径、来源定位、净文本和
用于引用的原文范围。标题文字不能充当全局主键，重复标题必须有不同位置 ID。
PDF 页码、DOCX 段落位置、文本行号等按可实际获得的信息记录，缺失时明确为空。
来源区间以解析所得文本为依据，不伪称 PDF 字节或版面坐标。

Markdown 使用标题层级，DOCX 使用真实标题样式；纯文本只识别受限、明确的
章节／条款标记。PDF 保留页码，对不确定的层级不做恢复。混合版式和表格不在
第一版中承诺支持。

切块先尊重明确的结构边界，再做有长度上限的分割。子片段能定位回原文区间；
超长句不可避免拆分时保留“原文片段”的标识，不声称是完整句或完整条款。

### 5.2 关系类型

- `section_member`：片段的章节归属；用于标题语境及定位，不自动返回整章。
- `adjacent`：同文档、同章节中的前后相邻片段；只是邻接信息，不是语义支持。
- `explicit_reference`：正文明确引用的同文档条款或章节，保存引用原文位置。

每条关系保存起点、终点、类型及解析依据。不存在或有多个可能目标的引用
保留为 unresolved，并报告原因；不选择字符串最接近的目标冒充解析成功。
第一版仅解析显式编号引用，不解析“上述规定”等指代，也不自动跨文档链接。

文档全部片段入库后再解析前向引用。完成状态、关系及词项索引应一致；中途
失败不得把半成品标为可用于新证据路径的完整文档。事务、普通状态字段、主键
和唯一约束用于这些一致性要求，不新增 hash 或冻结系统。

## 6. 核心证据、补充证据与预算

### 6.1 角色与边界

核心片段来自第 4 节排序。关联只从已选核心片段出发，第一版限一跳，不递归
扩展补充片段。已是核心的目标不重复返回，仍记录关联原因。

补充优先处理可唯一解析的显式引用，再考虑同章节相邻片段。邻接最多取直接
前后邻居，不因同章而遍历全章。章节标题作为定位元数据附在证据块上。
同一目标被多个核心引用时只输出一次，保留全部原因。

显式引用不等于事实支持；补充角色必须显示“引用目标”或“邻接语境”，不能
自动标注为“已验证条件”。结构缺失时返回可用核心证据，并标记无关联信息。

### 6.2 第一版选择规则

建议起始配置：最多 6 个不同片段、最多 2 个补充片段；默认上下文字符预算
6000，其中最多 30% 用于补充。各值均是可配置资源上限，不是学习出的最优值。

按排序贪心选择核心片段，默认先在 70% 的文本预算和 4 个片段名额内选择；
再按关系优先级、核心顺序和稳定目标 ID 尝试补充，确保显式引用优先于邻接。
配置总片段上限为 K、补充上限为 S 时，有效补充上限为 min(S, K-1)，首轮
核心名额为 K 减去有效补充上限；K 至少为一、S 不得为负。补充比例为零或
补充名额为零时不预留补充文本预算。其他情况下按所配比例预留。
剩余总预算可用于追加核心，追加后不再重新扩展，并记录该阶段未扩展的状态。
无补充时不强行填充无关联内容。所有比例必须在零到一之间且不能为一。

每次尝试都计算完整渲染块（包含标题、来源标签、原因标记、分隔符）的代价。
不够放入时跳过并记录原因；不在查询阶段偷偷截掉正文。没有任何完整核心块
可放入时返回“预算不足”，而非声称没有检索结果。若命中的引用目标由多块
组成但只纳入一部分，明确标记部分覆盖。

去重限于同一片段 ID、同来源重叠原文范围；不按向量相似度删除语义近似段落。
合并后的文本保持原文顺序，不能把中间遗漏内容伪装成连续原文。片段数量上限
按来源片段计数，不能靠合并输出块规避预算。

默认使用明确标注的字符预算，保证本地检索不需回答 API。支持注入回答模型
对应的本地 tokenizer 后可选 token 预算；无法获得时不自动换算，也不把
embedding tokenizer 计数宣称为真实生成 token。预算覆盖证据上下文，不包含
完整提示、用户问题及生成输出，不代表已经保证模型总上下文窗口不超限。

## 7. 数据库、接口和默认行为

新增 `evidence` 配置为拟定的新默认，旧五种配置名称和显式选择方式保留。
兼容入口仍返回三个值，新的结构化解释通过服务结果提供，菜单显示简短摘要。
`scores` 不再试图为补充项伪造相关性分数；新模式用可空分数及角色元数据，
旧模式仍保持其数值分数。调用者和测试需要覆盖这个明确的接口演进。

新结构索引需要原文重建，不能从旧库缺失的 metadata 中猜出来。首次升级
仅检查库版本和能力，不能通过构造存储对象隐式改写旧库。旧库可继续显式
使用旧模式；请求新模式时说明缺少什么及怎样重建，不静默退回 full。

重建是用户显式操作：输出到用户指定、尚不存在的新 SQLite 文件，原数据库
及文件保留。完成后显示如何显式切换配置，不自动覆盖原路径或重写用户 .env。
新路径首次建库无需旧库；现有 JSON 迁移流程不等同于结构重建，不能隐式串联。

新模式建库不默认生成旧共现图和 topic。旧图配置在缺少其所需索引时明确提示，
不假装已经启用，也不悄悄现场补建。纯向量读取可兼容有向量的两类库。

评测和实际服务都调用相同的候选预算与上下文组装逻辑。旧评测协议继续可用；
新协议记录最终实际上下文及核心／补充分别的数量、来源和预算单位。

## 8. 模块职责

保留现有 `config.py`、`embeddings.py`、`answering.py` 和兼容入口；尽量局部演进。
结构解析、词项检索、排名融合、关联解析和上下文组装分别作为小模块／独立
函数组织。`service.py` 负责调度与能力检查，不包揽排序算法。

SQLite 层提供受文档范围约束的词项查询、按 ID 批量取记录、按核心 ID 获取
局部关联，避免每问读取整张图。保留现有矩阵缓存及事务后的失效机制，不因
这次设计新增多层缓存或新的跨进程一致性承诺。

新模式文档范围先解析为唯一文档 ID；范围不明确时报错，不选择第一个名称
子串匹配项。所有召回和扩展都遵循该范围。

## 9. 验证与验收

先做普通单元测试及 CPU 集成测试，再考虑小规模 GPU 检索验证：

- RRF 空通道、缺失项、重复项、同分顺序与手算结果一致。
- 正常服务、旧 full 和比较入口均不突破配置的重排上限；零词项命中不扩大候选。
- 中文词项不跨标点拼接；标识符、空查询、特殊查询符号安全地作为字面词项处理。
- 向量和词项查询、关系扩展均不越过文档范围。
- 重复标题、前向引用、歧义引用、缺失结构不会产生伪造关系。
- 一跳上限、补充数量、实际渲染后的长度预算与来源去重均满足声明。
- 数值、日期及否定差异的近似文本不会因语义去重被删除。
- 模型不可用、FTS5 不可用、预算不足和旧库能力缺失均有明确错误或限制状态。
- 事务失败、续建、重复批次不会产生重复关系或把未完成索引标记为完成。
- 默认切换及旧公开入口的返回形态有兼容测试；旧库升级检查不改写数据库。

效果评估需要未用于规则调试的新文档／问题；自制结构 fixture 只证明实现，
不作为公开性能优势。区分核心来源召回、补充贡献、误扩展、实际上下文长度、
索引成本和查询延迟。相同模型、相同上下文预算比较，不能只取有利指标。
当前 400 文档／30 开发查询结果原样保留，不用新实现覆盖旧报告，不据其调参
后再将其称作独立测试。没有生成评估时不宣称答案质量已经提高。

本轮完成标准仅为设计自审及用户审阅；实现和效果验证在后续阶段分别报告。
